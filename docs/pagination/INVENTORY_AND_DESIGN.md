Baseline: clean Main `1efe3707`. Discovery only; no implementation changes made before this inventory. Sizes below are inferred from record lifecycle, not measured production cardinalities. CM means `/api/v1` on connection-manager. Sigma means `/api/v1` on sigma-engine. Repository paths abbreviated below resolve under the named service's `internal/` unless `pkg/api` is explicit. Every row is pending implementation/verification, not a completion claim.

User decisions: browse alerts by immutable creation time, show last-seen separately; build-only Dockerfile/Compose/go.mod changes authorized for one shared module. Runtime config/env and detection logic remain out of scope.

Grouped process/network analytics are measured separately with bounded windows and query deadlines, as approved by the user. The no-Sort/Seq-Scan requirement applies to indexable large-table row lists; no precomputed aggregate subsystem is introduced.

## Non-list records and internal consumers

- Health/readiness, stats/time buckets, capability catalogs, response action catalog and schema metadata are finite objects; do not paginate their keys or break their contracts.
- A process ancestor chain, playbook steps in a detail record, rule conditions, role permissions in a detail record and forensic bundle contents are parts of one object, not independent database pages. Standalone/history lists require pagination; details still expose all fields.
- Exception/scoring policy loaders, automation rule matching, unclaimed-alert sweeper, certificate revocation checking and rule seeding use repository methods internally. API pagination must not truncate internal detection/security data or mutate ingestion semantics.
- NDJSON signature feed is a machine protocol. A 100-row default cannot be applied in isolation: consumers must walk the feed completely before committing the version, including tied versions. Changes need protocol regression coverage.
- WebSocket alerts are incremental messages, not a historical REST page. Keep bounded buffers/reconciliation and gate visible updates behind a banner.
- Parity API wrappers and report generation depend on old shapes and local aggregation; their totals must not silently become totals for one page. Reports need explicit scope or bounded page-by-page export, never an unbounded fetch or silent truncation.

## Migrations and indexes

- CM latest embedded migration: 063_local_discovery_investigation. Next candidate 064 (not allocated/applied yet). Runner: connection-manager/internal/database/migrate.go, golang-migrate PostgreSQL driver. It also force-cleans dirty versions: do not rely on that behavior for partial concurrent-index recovery. Inspect driver's execution boundaries before choosing a concurrent migration file layout.
- Sigma latest embedded migration: 023_alert_last_seen. Next candidate 024 (not allocated/applied yet). Runner: sigma_engine_go/internal/infrastructure/database/migrate.go replays every embedded up file through one pool.Exec per file. Multiple SQL statements in one Exec can form an implicit transaction; concurrent indexes require one standalone statement per execution outside a transaction and explicit invalid-index recovery checks.
- Existing event indexes: (ts DESC), (agent_id,ts DESC), (event_type,ts DESC), (severity,ts DESC), GIN raw; missing id ties. Migration061 has partial (created_at,id) for autonomous events.
- Existing sigma alert indexes include timestamp, status/severity/agent-related keys, risk indexes, created_at from CM059, and partial (agent_id,rule_id,last_seen_at DESC) dedup index from Sigma023. Do not change dedup index/logic. Candidate browsing index is (created_at DESC,id DESC); common filter variants only after EXPLAIN validates usage.
- Existing audit/security/commands mostly have single-column created/issued indexes, insufficient by themselves to guarantee no sort at tied timestamps. Execution activity already has (trigger_source,updated_at,id), while history uses started_at indexes without id.
- Do not add every potential filter index. Build representative scratch datasets, retain plans and write-cost measurements before accepting migrations. Arbitrary text/JSON filters and grouped analytics cannot honestly be guaranteed to avoid Sort/Seq Scan in every case; report measured plans per supported query, with timeouts.

## Shared design

1. New local shared Go module with one pagination package imported by both services. Build contexts expanded narrowly to access it; no runtime config changes.
2. Default25/max100, reject malformed/negative limit/cursor/order/sort; clamp positive oversized limit. Cursor: version + endpoint/filter binding + fixed upper boundary + direction + full-precision immutable sort key/id. Strict bounded decode, integrity protection, no silent filter fallback. Query column identifiers come exclusively from endpoint-owned whitelist; values remain bound parameters.
3. Immutable creation/ingestion order for growing rows. Source event timestamp remains visible/filterable; paging on ingestion avoids late-arriving telemetry moving into an already traversed source-time page. Freeze browse upper bound at first page; new arrivals go into a refresh banner. A stateless walk cannot preserve historical membership if matching rows are deleted or mutable filters change mid-walk; do not promise MVCC snapshot guarantees without materializing/versioning results.
4. Reverse comparison/order plus in-memory reversal for previous page; fetch limit+1. Zero/NULL sort handling explicit; choose NOT NULL creation keys or indexed expression. Optional capped total only on request; lightweight SQL projections with detail endpoints for omitted payloads.
5. Small-list offset paging uses the same Page response and deterministic unique tie. Legacy shapes require explicit adapters and documented compatibility paths, still bounded.
6. Shared React query state owns URL filters/order/limit/cursor, backward/forward restoration, cancellation, stale result checks, placeholder previous data, cursor reset on search/filter/size changes, and retry/empty/loading states. Cursor/filters are part of cache identity. Visible selection clears on page/filter changes; no action silently applies to unseen rows.
7. Live updates do not move visible rows. Count queued new/changed records with bounded dedup state; click refresh resets to first page. Pause hidden-tab polling; no automatic replacement of older pages.
8. Query deadlines and migration/write cost measured independently from rendering. No destructive migration, production data changes, commit or push.
